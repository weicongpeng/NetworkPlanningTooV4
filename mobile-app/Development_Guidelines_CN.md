# 开发指南

- 偏向谨慎而非速度，简单任务请自行判断。

## 1. 核心信念

- **渐进优于大改** — 小步提交，每次都能编译通过、测试通过
- **先学后做** — 研究现有代码和模式再动手
- **务实优于教条** — 适应项目现实
- **清晰优于聪明** — 选无聊但显而易见的方案

## 2. 先想后写

**不假设、不隐藏困惑、呈现权衡。**

- 明确陈述假设，不确定就问
- 存在多种理解时，全部列出——不要静默选择
- 有更简单的方案就说出来，必要时反驳
- 不清楚就停下来，指出困惑之处再问

## 3. 简单优先

**最少代码解决问题，不写投机性内容。**

- 不做超出要求的功能
- 不为单次使用创建抽象
- 不添加未要求的"灵活性"或"可配置性"
- 不为不可能发生的场景写错误处理
- 200 行能写成 50 行，就重写
- 问自己："高级工程师会觉得这太复杂了吗？" 如果是，简化。

## 4. 精准修改

**只改必须改的，只清理自己弄乱的。**

- 不"改进"相邻代码、注释或格式
- 不重构没坏的东西
- 匹配现有风格，即使你会用不同写法
- 发现无关死代码，提一句——不要删
- 你的改动产生的孤立代码（未使用的 import/变量/函数），必须移除
- 已有的死代码，除非被要求否则不删

**检验标准：每一行改动都应能追溯到用户的需求。**

## 5. 目标驱动执行

**定义可验证的成功标准，循环直到验证通过。**

将任务转化为可验证目标：
- "加验证" → "为无效输入写测试，然后让它通过"
- "修 Bug" → "写一个能复现的测试，然后让它通过"
- "重构 X" → "确保重构前后测试都通过"

多步任务，先列简要计划：
```
1. [步骤] → 验证: [检查方式]
2. [步骤] → 验证: [检查方式]
3. [步骤] → 验证: [检查方式]
```

强成功标准让你能独立循环；弱标准（"让它能用"）则需要不断澄清。

## 6. 规划与分阶段

- 复杂工作拆为 3-5 个阶段，记录在 `IMPLEMENTATION_PLAN.md`：

```markdown
## Stage N: [名称]
**Goal**: [具体交付物]
**Success Criteria**: [可测试的结果]
**Tests**: [具体测试用例]
**Status**: [Not Started | In Progress | Complete]
```

- 随进展更新状态
- 全部完成后删除该文件

## 7. 实现流程

1. **理解** — 研究代码库中的现有模式
2. **测试** — 先写测试（红）
3. **实现** — 最少代码通过测试（绿）
4. **重构** — 测试通过下清理
5. **提交** — 清晰的提交信息，关联计划

## 8. 卡住时（3 次尝试后）

**关键：同一问题最多尝试 3 次，然后停下。**

1. **记录失败**：尝试了什么、具体错误信息、失败原因推测
2. **研究替代方案**：找 2-3 个类似实现，记录不同做法
3. **质疑根本假设**：抽象层级对吗？能拆成更小问题吗？有没有更简单的路？
4. **换个角度**：不同的库/框架特性？不同的架构模式？删掉抽象而不是加？

## 9. 架构原则

- **组合优于继承** — 使用依赖注入
- **接口优于单例** — 便于测试和灵活扩展
- **显式优于隐式** — 清晰的数据流和依赖关系

## 10. 错误处理

- 快速失败，附带描述性信息
- 包含调试上下文
- 在合适的层级处理错误
- 绝不静默吞掉异常

## 11. 决策框架

多种可行方案时，按以下顺序选择：

1. **可测试性** — 能轻松测试吗？
2. **可读性** — 6 个月后能看懂吗？
3. **一致性** — 符合项目既有模式吗？
4. **简单性** — 是能工作的最简方案吗？
5. **可逆性** — 后续改动成本多高？

## 12. 项目集成

### 学习代码库
- 找 3 个类似的功能/组件
- 识别通用模式和约定
- 尽量使用相同的库/工具
- 遵循现有测试模式

### 工具链
- 使用项目现有的构建系统
- 使用项目现有的测试框架
- 使用项目现有的格式化/lint 配置
- 没有充分理由不引入新工具

## 13. 质量门禁

### 完成定义

- [ ] 测试已写且通过
- [ ] 代码符合项目约定
- [ ] 无 linter/formatter 警告
- [ ] 提交信息清晰
- [ ] 实现与计划一致
- [ ] 无未关联 issue 的 TODO

### 测试准则

- 测试行为，不测实现
- 尽量一个断言一个测试
- 测试名称清晰描述场景
- 使用现有测试工具/辅助函数
- 测试必须确定性可重复

### 每次提交必须

- 编译成功
- 所有已有测试通过
- 新功能有对应测试
- 遵循项目格式/lint 规则
- 提交信息解释"为什么"

## 14. 重要提醒

**绝不**：
- 用 `--no-verify` 绕过提交钩子
- 禁用测试而不是修复测试
- 提交无法编译的代码
- 凭假设行事——用现有代码验证

**始终**：
- 增量提交可工作的代码
- 随进展更新计划文档
- 从现有实现中学习
- 3 次失败后停下重新评估

---
**这些准则有效的标志：** diff 中不必要改动更少、因过度复杂而重写更少、澄清问题出现在实现之前而非犯错之后。
